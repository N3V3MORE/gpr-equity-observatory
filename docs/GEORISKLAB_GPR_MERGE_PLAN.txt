GeoRiskLab + GPR Equity Observatory Merge Plan
Generated: 2026-06-26

Purpose
=======

This plan records where the two projects live locally and on GitHub, what each
project currently does, what is risky in the current working trees, and the best
practical path for combining them.

The recommended merge is not a blind file copy or raw history merge. The safest
and most useful combined project should keep GPR Equity Observatory as the main
public Streamlit research product, then port GeoRiskLab's stronger
reproducibility, provenance, validation, sample/real mode, and monthly
benchmark pipeline into it in staged slices.

5. Recommended Merge Strategy
=============================

Recommendation
--------------

Use GPR Equity Observatory as the destination repository and product identity.
Port GeoRiskLab into GPR in phases as infrastructure and a monthly benchmark.

Recommended destination:
C:\Users\Sushmit\Desktop\Code\GPR_Observer

Recommended public repo after merge:
https://github.com/N3V3MORE/gpr-equity-observatory

Recommended combined product name:
GPR Equity Observatory

Optional subtitle:
Powered by GeoRiskLab research infrastructure

Why GPR should be the destination
---------------------------------

1. It already has the stronger public product.

   The Streamlit dashboard, screenshots, README, results brief, and profile docs
   make it better as the visible project.

2. It has the richer daily empirical analysis.

   The GPR app covers more analysis modes and a 20-country ETF panel.

3. It is already structured as the user's profile-ready output.

   Renaming the public project to GeoRiskLab would make the existing docs and
   dashboard less coherent.

4. GeoRiskLab's best parts are portable.

   Its provenance, validation, task runner, sample/real separation, and monthly
   benchmark can be imported without forcing a full identity swap.

Why not use a raw Git merge
---------------------------

A raw merge of repositories or a full copy of GeoRiskLab into GPR would create
several avoidable problems:

- duplicate package roots: src/gprobs and georisklab
- duplicate scripts with overlapping names
- conflicting data policies
- conflicting generated-output policies
- two dashboard systems
- different Python versions
- different packaging backends
- different line lengths
- ambiguous "real" versus "sample" outputs
- ambiguous daily versus monthly analysis results

Better approach:
- Start with a clean GPR branch.
- Add GeoRiskLab as a remote only for reference.
- Port code module-by-module with tests.
- Preserve provenance and validation semantics.
- Keep monthly benchmark outputs separate from daily outputs.

Repository strategy options
---------------------------

Option A: Single merged repository, GPR as destination.

Recommended.

Shape:
- Keep src/gprobs as the package.
- Port GeoRiskLab modules into src/gprobs under clear names.
- Keep Streamlit app.py as primary UI.
- Add monthly benchmark tabs to Streamlit only after outputs are stable.
- Add task runner or Makefile-style Python runner for repeatable commands.

Pros:
- One public project.
- One dashboard.
- One test suite.
- One docs set.
- Easiest profile story.
- Best for future users.

Cons:
- Requires careful module mapping.
- Requires decisions about sample outputs and generated artifacts.

Option B: Monorepo with both packages.

Acceptable but not recommended for this project stage.

Shape:
- Keep src/gprobs.
- Add georisklab/ as a second package.
- Adjust pyproject to include both packages.
- Streamlit imports georisklab where useful.

Pros:
- Less initial code movement.
- Easier to preserve GeoRiskLab history and package boundaries.

Cons:
- Public story becomes muddier.
- Two packages for one small research project is likely overkill.
- Duplicated concepts will linger longer.
- More import and packaging complexity.

Option C: Keep repos separate and integrate through dependency.

Not recommended unless GeoRiskLab is meant to become a general toolkit.

Shape:
- Publish or install georisklab as a dependency of GPR.
- GPR imports georisklab for monthly/provenance features.

Pros:
- Clean separation.
- GeoRiskLab remains independently reusable.

Cons:
- Slower iteration.
- Harder local setup.
- Two repos to maintain.
- Harder for profile reviewers to understand.

Final recommendation:
Use Option A.

10. Data and Research Interpretation Rules
==========================================

These rules should survive the merge.

1. No trading-system framing.

   This is an educational/applied economics project, not investment advice.

2. No causal claims from simple regressions.

   Use language like:
   - associated with
   - conditional response
   - benchmark estimate
   - within this validation design

   Avoid:
   - proves
   - causes
   - tradeable signal
   - markets are inefficient

3. Sample mode is not evidence.

   Sample mode proves the workflow runs. It does not support empirical claims.

4. Real mode must show provenance.

   Any real-data output must have:
   - source manifest
   - input period
   - source hashes where applicable
   - clear source descriptions
   - validation status

5. Daily and monthly findings are not interchangeable.

   Daily ETF event studies and monthly aggregate Fama-French benchmarks answer
   related but different questions.

6. Two-market aggregate monthly results are limited.

   They are useful as a benchmark but not as credible country-clustered panel
   inference.

7. GDELT and macro controls require explicit real-data validation.

   Until real inputs exist, they should be described as staged extensions or
   sample-mode software checks.
